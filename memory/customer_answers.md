# 顧客に聞かれたら即答する用

**PM目線の言葉で、「事業・コスト・リスクにどう効くか」を主語にする。**技術的な正確さより伝わることを優先。

## なぜ MySQL か
1. **設計書が最初からMySQL前提**。DDL・インデックス・照合順序まで書かれており、変える理由が無い
2. **RDSのフルマネージドで運用負荷が小さい**。バックアップとPITRが標準で付く
3. **技術者の確保が容易**。引き継ぎのリスクが低い
(正直な経緯: ゼロベースなら他の選択肢もあったが、設計書の資産を捨てるコストの方が大きい。**共通ID基盤はPostgreSQLだが別システムで、揃える必要はない**)

## なぜモバイル専用UIを作らないか
1. **工期**: 専用UIは+2〜4週。レスポンシブ化なら+1.5人日
2. **保守**: 案件管理だけで11セクション・140項目。仕様変更のたびに2箇所直すことになる
3. **セキュリティ(決め手)**: 画面が2系統になると**権限による出し分けも2箇所で実装**することになり、片方の実装漏れがそのまま「見えてはいけない人に見える」事故になる
4. モバイルのデザインモックが存在しないので、作れば設計書に根拠のない実装が大量に発生する

## なぜ WAF・IP制限を入れないか
- **モバイル対応を決めた以上、IP制限は現実的でない**(外出先から使えなくなる)
- 代わりに無料でできる代償措置を10点入れている(SSHは公開鍵認証のみ・root禁止・fail2ban・認証失敗の急増をSlack通知・セキュリティヘッダー・アプリ層の防御をCIで強制 など)
- **受け入れているリスクも明示してある**: アプリ層に未知の脆弱性があれば直接突かれる / 大規模DDoSにはEC2 1台では耐えられない
- **見直しのトリガーを決めてある**: 認証失敗のアラートが発火する / 社外の人間にアカウントを発行する / 個人情報の取扱量が大きく増える

## なぜ外部サービス(Sentry等)を使わないか
- 小林さんの判断(2026-08-05)。**これによりAWSの外に出るのはGitHubと外部API3種(郵便番号・銀行コード・法人番号)だけになり、施主の個人情報がAWS外に出る経路が無くなった**
- 代替: エラー収集はCloudWatch Logs + 自前のエラー受信API / カバレッジはCIのPRコメント

## なぜ月1万円で足りるのか
- **同時利用50名の社内システム**だから。設計書の構成(月6〜7万円)は数百人規模の商用サービス向け
- **落ちて困る規模になってから冗長化を足せる**。Terraformの変数を変えてapplyするだけで対応できるようにしてある
- **ただしバックアップと添付ファイルの永続化は削っていない。**事故後に取り戻せないため
